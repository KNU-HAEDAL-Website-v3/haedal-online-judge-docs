# 5. P1 인증 — 세션 + 인터셉터 채택, Spring Security 보류

- 날짜: 2026-08-14 · 상태: 확정

## 결정

P1 인증은 **HttpSession 쿠키 + HandlerInterceptor(default-deny) + @LoginUser 리졸버**로 직접 구현한다.
Spring Security와 JWT는 P1에서 사용하지 않는다. 신원 확인은 `AuthService` 인터페이스 뒤에 격리하고,
개발 중에는 `StubAuthService`(무조건 신뢰), 홈페이지 연동 확정 시 구현체만 교체한다.

## 근거

1. **팀 학습 부하.** Spring Security의 필터체인·인증객체 모델은 학습 곡선이 가파르다. 백엔드 주니어가 코드를 "읽고 복제"할 수 있어야 하는데, 시큐리티가 끼면 마법 상자가 하나 더 늘어난다.
2. **우리 권한 모델과 안 맞는다.** HOJ의 권한은 "분반 범위 역할"(Enrollment.role)이 핵심인데, 이는 시큐리티의 전역 Role 모델로 표현이 안 되고 결국 커스텀 판정 컴포넌트를 짜야 한다. 그 커스텀이 어차피 필요하다면 그 밑의 프레임워크는 단순할수록 좋다.
3. **JWT 대비 세션의 이점.** 단일 서버라 세션 공유 문제가 없고, 서버 측 무효화(강제 로그아웃)가 즉시 되며, 토큰 만료/갱신 로직이 통째로 필요 없다. localhost는 포트가 달라도 same-site라 개발 중 쿠키도 문제없다.

## 감수하는 것

- 서버 재시작 시 전원 로그아웃(인메모리 세션) — 동아리 도구 규모에서 수용.
- 새 경로 면제는 WebConfig excludePathPatterns 한 곳에서만 관리해야 함.

## 재검토 조건

서버 수평 확장, 모바일 네이티브 클라이언트 등장, 또는 홈페이지 SSO가 JWT 발급 방식으로 확정되는 경우(그때는 토큰 검증 AuthService 구현 + 필요 시 세션 → 토큰 전환).
